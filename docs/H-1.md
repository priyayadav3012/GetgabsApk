# H-1 — `onIncomingVoipCall` method channel call silently dropped before Dart is ready

## Problem

When a VoIP push arrives with the app killed or backgrounded, `AppDelegate` writes call metadata to `NSUserDefaults` and then dispatches a method channel call:

```swift
DispatchQueue.main.async { [weak self] in
    self?.callChannel?.invokeMethod(
        "onIncomingVoipCall",
        arguments: ["uuid": uuidString, "callerName": callerName]
    )
}
```

`callChannel` is non-nil (it was created in `didFinishLaunchingWithOptions`), so the call appears to succeed. But on the Dart side, the method call handler set up in `initMethodChannel()` may not yet be registered — the Flutter engine initialises asynchronously after `didFinishLaunchingWithOptions` returns. If the Dart isolate hasn't processed its first frame yet, the method call is delivered to a channel with no registered handler and is silently discarded.

The fallback path — `checkPendingAnsweredCall` polled from `initMethodChannel` — was also called with `Duration.zero`, meaning it fired on the very next event-loop tick. At that point the Dart-to-native bridge may still be unready, and the channel invocation could fail silently for the same reason.

## Fix

**File**: `lib/domain/end_points/api_end_points.dart`

Increase the `checkPendingAnsweredCall` delay from `Duration.zero` to `300 ms`. This gives the Flutter engine enough time to render its first frame and register all channel handlers before the poll fires.

```dart
// BEFORE — fires on the next event-loop tick, Dart may not be ready
Future<void>.delayed(Duration.zero, () async {
  final result = await platform.invokeMethod('checkPendingAnsweredCall');
  // ...
});

// AFTER — 300 ms gives the engine time to settle and register handlers
Future<void>.delayed(const Duration(milliseconds: 300), () async {
  final result = await platform.invokeMethod('checkPendingAnsweredCall');
  // ...
});
```

## How It Works

`initMethodChannel()` is called from `main()` after `Firebase.initializeApp()` and before `runApp()`. The Flutter engine starts its Dart isolate during `runApp()` and registers plugin handlers over several event-loop cycles. A 300 ms delay ensures the isolate has completed initialisation and `platform.setMethodCallHandler` is active before `checkPendingAnsweredCall` fires.

The `onIncomingVoipCall` channel call from AppDelegate remains best-effort (it fires ~200 ms after the push, which may still be before Dart is ready on very slow devices). The `checkPendingAnsweredCall` poll at 300 ms is the reliable safety net: if `onIncomingVoipCall` was missed, `checkPendingAnsweredCall` reads the same `pendingAnsweredCallUUID` that `CallManager.tryNotifyFlutter` cached and triggers the answer flow.
