# M-2 — Redundant `handlePendingCallNavigation()` in `onReady` — premature/stale nav risk

## Problem

`GetMaterialApp.onReady` called `handlePendingCallNavigation()` immediately after the first frame:

```dart
onReady: () {
    _initializeCallListener();
    WhatsAppCallingConfig.handlePendingCallNavigation();  // ← premature
},
```

`handlePendingCallNavigation()` reads and clears `_pendingNavigation`. At the time `onReady` fires (typically < 100 ms after app launch), `_checkInitialCall()` has not yet run — it waits 1,500 ms before reading SharedPreferences and calling `storePendingNavigation()`. So `_pendingNavigation` is `null` and this call is always a no-op for the killed-state flow.

**However**, there are two risk scenarios:

1. **Stale navigation data**: If `_pendingNavigation` was somehow set before `onReady` (e.g., from a previously answered call whose `cleanupCall()` did not complete), `onReady` would navigate to `WhatsAppCallingScreen` before the WebRTC service is initialised — resulting in a dead call screen.

2. **Future regression**: If any code path before `onReady` calls `storePendingNavigation()` (e.g., a push notification handler that fires synchronously), `onReady` would consume and clear `_pendingNavigation` before `_checkInitialCall` sets up the service, causing the real navigation attempt (with a live service) to find `_pendingNavigation == null` and silently skip.

The correct owners of navigation are:
- `_checkInitialCall` (killed-state startup — reads prefs, sets up service, then navigates)
- `onNativeCallAnswered` channel handler (user answered from CallKit)
- `CallEventActionCallAccept` (user answered from plugin CallKit / Android)
- `AppLifecycleObserver.didChangeAppLifecycleState` (foreground resume)

## Fix

**File**: `lib/main.dart`

Remove the `handlePendingCallNavigation()` call from `onReady`. Keep `_initializeCallListener()` there (it is the right place — initialise background service after first frame, but do not navigate).

```dart
// BEFORE
onReady: () {
    _initializeCallListener();
    WhatsAppCallingConfig.handlePendingCallNavigation();  // ← removed
},

// AFTER
onReady: () {
    _initializeCallListener();
    // Navigation owned by _checkInitialCall / onNativeCallAnswered / CallEventAction
},
```

## How It Works

Removing the call makes `onReady` responsible only for background service setup. Navigation happens later, via the path that has already set `_pendingNavigation` and set up the service. Because `handlePendingCallNavigation` consumes and clears `_pendingNavigation` atomically, any future stale-data bug now fails closed (navigation is skipped) rather than opening a dead call screen.
