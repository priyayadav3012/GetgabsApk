# H-3 — `CALL_ANSWERED_NATIVE` observer registered but never fired — dead code

## Problem

`AppDelegate` registered an `NSNotificationCenter` observer for the name `"CALL_ANSWERED_NATIVE"`:

```swift
NotificationCenter.default.addObserver(
    self,
    selector: #selector(handleNativeCallAnswered(_:)),
    name: NSNotification.Name("CALL_ANSWERED_NATIVE"),
    object: nil
)
```

`handleNativeCallAnswered` was designed to:
1. Try to invoke `callChannel?.invokeMethod("onNativeCallAnswered", ...)`.
2. If `callChannel` was nil (Flutter not yet ready), cache the UUID in `pendingAnsweredCallUUID` so `checkPendingAnsweredCall` could retrieve it later.

**But `CallManager` never posted the `"CALL_ANSWERED_NATIVE"` notification.** The answer action `provider(_:perform:CXAnswerCallAction)` called `tryNotifyFlutter` directly and nothing else. The observer and its entire logic path — including the `pendingAnsweredCallUUID` caching that `checkPendingAnsweredCall` depended on — was dead code. `pendingAnsweredCallUUID` was only ever set inside `tryNotifyFlutter` after 20 failed retries (10 s), meaning:

- The `handleNativeCallAnswered` path never executed.
- The `checkPendingAnsweredCall` check in Flutter rarely found a value because it polled at startup (before the 10 s retry window expired).

## Fix

### `ios/Runner/CallManager.swift`

Post `"CALL_ANSWERED_NATIVE"` at the start of the answer action, before `tryNotifyFlutter`. This fires the observer in AppDelegate immediately and caches `pendingAnsweredCallUUID` right away — so if the Flutter channel is not ready, `checkPendingAnsweredCall` finds the UUID on its first poll (300 ms after `initMethodChannel`, see H-1).

```swift
// Added — post notification so AppDelegate observer runs immediately
NotificationCenter.default.post(
    name: NSNotification.Name("CALL_ANSWERED_NATIVE"),
    object: nil,
    userInfo: ["uuid": uuid]
)
// tryNotifyFlutter runs in parallel as a belt-and-suspenders retry
tryNotifyFlutter(uuid: uuid, attempt: 0)
```

### `ios/Runner/AppDelegate.swift`

No functional change — the observer was already wired correctly. Added a clarifying comment explaining that `handleNativeCallAnswered` is the last-resort cache path when `tryNotifyFlutter` exhausts all 20 retries.

## How It Works

Two complementary paths now notify Flutter that a call was answered:

| Path | When it works | Mechanism |
|------|--------------|-----------|
| `tryNotifyFlutter` retry loop | Flutter engine starts within ~10 s | 20 × 0.5 s retries calling `invokeMethod("onNativeCallAnswered")` |
| `CALL_ANSWERED_NATIVE` → `handleNativeCallAnswered` → `pendingAnsweredCallUUID` → `checkPendingAnsweredCall` | Flutter engine takes > 10 s (rare, slow device) | UUID cached in AppDelegate; Flutter polls at startup |

Both paths are now live, providing defence in depth for the killed-state answer flow.
