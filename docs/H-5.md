# H-5 — `CURLOPT_TIMEOUT => 0` in `sendFcm()` — queue worker hangs indefinitely

## Problem

`sendFcm()` built cURL options with:

```php
CURLOPT_TIMEOUT => 0,
```

`CURLOPT_TIMEOUT = 0` means "no timeout" — if the FCM endpoint is unreachable, slow, or returns a stall response, the cURL call blocks forever. The Laravel queue worker process is single-threaded per job; a hung cURL call freezes the entire worker, preventing any subsequent jobs from executing until the process is killed and restarted by the supervisor.

The job itself declares `public int $timeout = 30`, but that is the job-level timeout enforced by the queue runner (it sends `SIGKILL` to the worker after 30 s). However, `SIGKILL` on the worker process causes the job to be re-queued and retried, amplifying the problem rather than resolving it.

## Fix

**File**: `SendCallFcmNotificationJob.php` — `sendFcm()` method

```php
// BEFORE
CURLOPT_TIMEOUT => 0,   // no timeout — hangs forever

// AFTER
CURLOPT_TIMEOUT => 10,  // 10 s is more than enough for FCM
```

## How It Works

FCM's HTTP v1 endpoint (`fcm.googleapis.com`) responds in under 1 s under normal conditions. A 10-second timeout is generous enough to survive transient slowness while preventing permanent hangs. If FCM doesn't respond within 10 s there is a network-level problem; the job will fail, log the cURL error, and the queue runner will retry it (up to `$tries = 2` attempts) rather than blocking the worker thread.
