# M-5 — Hardcoded 2-second delay in `_initializeCallListener()` — unnecessary startup lag

## Problem

`_initializeCallListener()` in `lib/main.dart` delayed initialisation for 2 seconds before setting up `GlobalCallListenerService`:

```dart
Future<void> _initializeCallListener() async {
    await Future.delayed(const Duration(seconds: 2));  // ← hardcoded wait
    await WhatsAppCallingConfig.initializeCallListener();
}
```

This function is called from `onReady` (after the first frame is rendered). The 2-second delay was added as a workaround to let the app "settle", but it causes two concrete problems:

1. **Incoming call while app is opening**: If a VoIP push arrives and the user answers before the 2-second delay expires, `GlobalCallListenerService.instance.service` is still `null` when `onNativeCallAnswered` fires. The H-6 fix checks `existingSvc == null` and calls `initializeCallListener()` in that case, but this adds another initialisation round-trip on the answer path.

2. **Normal usage**: Every time the app starts — including normal foreground use — socket connection to the signalling server is delayed by 2 seconds. If an outgoing call is initiated within those 2 seconds, the socket isn't ready.

The delay was never necessary because `initializeCallListener()` already reads from persistent storage (GetStorage/SharedPreferences) and returns early if `userId == 0`. The Dart isolate is fully running when `onReady` fires; there is nothing to wait for.

## Fix

**File**: `lib/main.dart`

Remove the `Future.delayed` call. `_initializeCallListener()` now calls `initializeCallListener()` directly:

```dart
// BEFORE
Future<void> _initializeCallListener() async {
    await Future.delayed(const Duration(seconds: 2));
    await WhatsAppCallingConfig.initializeCallListener();
}

// AFTER
Future<void> _initializeCallListener() async {
    await WhatsAppCallingConfig.initializeCallListener();
}
```

## How It Works

`WhatsAppCallingConfig.initializeCallListener()` already guards against premature init (returns early if `userId == 0` or if a service is already running with an active call). Removing the artificial delay means the socket connects as soon as the app renders its first frame, making it ready before the user can tap anything. The `_checkInitialCall` 1,500 ms delay (for killed-state prefs read) is unaffected — that is a different code path.
