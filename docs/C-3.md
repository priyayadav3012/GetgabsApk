# C-3 — `call_terminated` sent to VoIP APNs token — always rejected by Apple

## Problem

Apple's APNs enforces a strict rule: a VoIP device token (`PKPushType.voIP`) may **only** receive pushes with `apns-push-type: voip`. Sending any other push type to a VoIP token returns HTTP 400 with error `InvalidPushType` or `BadDeviceToken`.

`sendApnsVoip()` was called unconditionally for every notification type, including `call_terminated`. For a terminated call it built an **alert** push:

```php
$apsBlock = [
    'alert' => ['title' => $notifTitle, 'body' => 'Call Ended'],
    'sound' => 'default',
    'badge' => 1,
];
$pushType = 'alert';
```

…and sent it to the VoIP device token with `apns-push-type: alert`. APNs rejected every one of these silently (from the server's perspective the cURL call completed with HTTP 400, but the job had no error handling for non-200 on the VoIP path).

**Effect on the user**: When a caller hung up, the server sent:
1. FCM topic notification → Flutter background handler → `FlutterCallkitIncoming.endCall()` ✓ (this path worked)
2. Direct APNs VoIP token → rejected → nothing happened

Because path 1 worked, the CallKit UI usually dismissed. But on iOS, if the FCM arrived late or the background handler was throttled by Low Power Mode, the VoIP rejection meant there was no backup — the native CallKit ring screen stayed visible until its 60-second `duration` timeout.

## Fix

**File**: `SendCallFcmNotificationJob.php`

Wrap the entire VoIP push block in a `$this->type === 'incoming_call'` guard. `call_terminated` (and any future type) never reaches the VoIP push path.

```php
// BEFORE — called sendApnsVoip() for all types including call_terminated
$userIds = array_filter([$this->userId, $this->subUserId]);
if (!empty($userIds)) {
    $iosTokens = DB::table('user_device_tokens')
        ->whereIn('user_id', $userIds)
        ->whereNotNull('ios_voip_token')
        ->where('ios_voip_token', '!=', '')
        ->pluck('ios_voip_token');

    foreach ($iosTokens as $token) {
        $this->sendApnsVoip($token);   // ← sent alert push to VoIP token → rejected
    }
}

// AFTER — VoIP push only for incoming_call
if ($this->type === 'incoming_call') {
    $userIds = array_filter([$this->userId, $this->subUserId]);
    if (!empty($userIds)) {
        $iosTokens = DB::table('user_device_tokens')
            ->whereIn('user_id', $userIds)
            ->whereNotNull('ios_voip_token')
            ->where('ios_voip_token', '!=', '')
            ->pluck('ios_voip_token');

        foreach ($iosTokens as $token) {
            $this->sendApnsVoip($token);
        }
    }
}
```

## How It Works

VoIP tokens exist solely so iOS can wake a killed app and present a CallKit UI for an *incoming* call. There is no APNs-level mechanism to "dismiss" a call using a VoIP push — call termination on iOS is handled by `FlutterCallkitIncoming.endCall()` triggered by the FCM `call_terminated` data message. Keeping the VoIP path strictly to `incoming_call` respects Apple's API contract, eliminates the APNs 400 rejections, and avoids any risk of Apple revoking the VoIP push entitlement for policy violations.
