# H-2 — `setupAudioSession()` called before `didActivate` — audio configuration race

## Problem

`CXProviderDelegate.provider(_:perform:CXAnswerCallAction)` was:

```swift
public func provider(_ provider: CXProvider, perform action: CXAnswerCallAction) {
    action.fulfill()          // 1. tells CallKit the answer was accepted
    setupAudioSession()       // 2. configures WebRTC audio — TOO EARLY
    tryNotifyFlutter(...)     // 3. notifies Flutter
}
```

`action.fulfill()` signals CallKit that the app has accepted the call. CallKit then asynchronously activates the audio session and calls `provider(_:didActivate:)`. This activation is **asynchronous** — it happens on a subsequent run-loop cycle, not inline.

Calling `setupAudioSession()` immediately after `action.fulfill()` meant `RTCAudioSession.setConfiguration()` ran while the audio session was still in its pre-activation state. The result was:
- `AVAudioSession.setCategory(.playAndRecord)` on an inactive session — silently ignored or partially applied.
- When `didActivate` eventually fired, `rtcSession.audioSessionDidActivate(audioSession)` and `rtcSession.isAudioEnabled = true` ran **without** the correct category/mode being set.
- Intermittently: no audio on the answered call, or audio only in one direction.

## Fix

**File**: `ios/Runner/CallManager.swift`

Remove `setupAudioSession()` from the answer action. Move it to the top of `provider(_:didActivate:)`, which fires only after the system has successfully activated the session.

```swift
// BEFORE
public func provider(_ provider: CXProvider, perform action: CXAnswerCallAction) {
    action.fulfill()
    setupAudioSession()        // ← too early, session not yet active
    tryNotifyFlutter(...)
}

public func provider(_ provider: CXProvider, didActivate audioSession: AVAudioSession) {
    let rtcSession = RTCAudioSession.sharedInstance()
    rtcSession.audioSessionDidActivate(audioSession)
    rtcSession.isAudioEnabled = true
}

// AFTER
public func provider(_ provider: CXProvider, perform action: CXAnswerCallAction) {
    action.fulfill()
    // setupAudioSession() removed — deferred to didActivate
    tryNotifyFlutter(...)
}

public func provider(_ provider: CXProvider, didActivate audioSession: AVAudioSession) {
    setupAudioSession()        // ← configure first, then notify WebRTC
    let rtcSession = RTCAudioSession.sharedInstance()
    rtcSession.audioSessionDidActivate(audioSession)
    rtcSession.isAudioEnabled = true
}
```

## How It Works

The correct lifecycle sequence is:

1. User taps Answer → `perform action: CXAnswerCallAction` fires → `action.fulfill()`.
2. CallKit activates the `AVAudioSession` with the category/mode it has already reserved for the call.
3. `provider(_:didActivate:)` fires — the session is now fully active and owned by the app.
4. **`setupAudioSession()`** configures the WebRTC `RTCAudioSessionConfiguration` (category, mode, Bluetooth options) on an already-active session — the call to `setCategory` is honoured by the system.
5. `audioSessionDidActivate` and `isAudioEnabled = true` tell the WebRTC engine it can start sending/receiving audio.

This order guarantees the audio category is applied before WebRTC starts processing, preventing one-way or no audio on answered calls.
