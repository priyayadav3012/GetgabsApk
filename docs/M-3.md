# M-3 — `notification` block in `call_terminated` FCM message triggers unwanted system banner

## Problem

The FCM message builder set `notification` conditionally:

```php
'notification' => $this->type === 'incoming_call'
    ? null
    : ['title' => $notifTitle, 'body' => $notifBody],
```

For `call_terminated`, a `notification` block with `title: "<caller name>"` and `body: "Call Ended"` was sent. This caused two problems:

1. **iOS**: FCM `notification` blocks are routed to APNs as `apns-push-type: alert`. On iOS a notification alert is displayed by the system, even when the app is in the background. Users would see a notification banner reading "Call Ended" after every call, cluttering the notification centre.

2. **Android**: The FCM SDK displays a system notification tray entry for a `notification` payload when the app is in the background. For a `call_terminated` event that arrives while the call screen is still showing, this displayed an extra "Call Ended" notification alongside (or after) the in-app UI that already handled the end.

Both cases are already handled in-app: `onCallEndedNatively` (iOS CallKit) and the Socket.IO `call_ended` event (both platforms) dismiss the call screen and clean up. The `notification` block adds nothing and creates noise.

## Fix

**File**: `SendCallFcmNotificationJob.php`

Set `notification` to `null` for all message types. Both `incoming_call` and `call_terminated` are fully data-only messages — all presentation is handled natively (CallKit for iOS, `flutter_callkit_incoming` for Android) or in-app.

```php
// BEFORE — call_terminated sent a visible notification
'notification' => $this->type === 'incoming_call'
    ? null
    : ['title' => $notifTitle, 'body' => $notifBody],

// AFTER — always null; no system banner for any call event
'notification' => null,
```

The existing `if ($message['message']['notification'] === null) { unset(...); }` block beneath already strips the null key from the serialised JSON, so the API request is clean.

## How It Works

FCM's HTTP v1 API: when `notification` is absent from the message, the system does not auto-display any notification. The `data` payload is delivered silently to the app's `onMessage` / background handler. The app decides whether and how to present UI — which for calls is always via CallKit or `flutter_callkit_incoming`, not system notifications. Removing the `notification` block for `call_terminated` eliminates the unwanted banner while leaving the `incoming_call` path unchanged (it was already `null`).
