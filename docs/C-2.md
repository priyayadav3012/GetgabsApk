# C-2 — Two competing CXProvider instances cause duplicate CallKit UI

## Problem

The app ran two independent CallKit stacks simultaneously on iOS:

1. **Native stack** — `CallManager.swift` holds a `CXProvider` instance. When a PushKit VoIP push arrives, `AppDelegate.pushRegistry(_:didReceiveIncomingPushWith:)` calls `CallManager.shared.reportIncomingCall()`, which calls `provider.reportNewIncomingCall(with:update:)`. iOS shows the native CallKit UI.

2. **Plugin stack** — `flutter_callkit_incoming` holds its *own* `CXProvider`. `_firebaseMessagingBackgroundHandler` called `FlutterCallkitIncoming.showCallkitIncoming()`, which called `provider.reportNewIncomingCall(with:update:)` on the plugin's provider.

`FlutterCallkitIncoming.activeCalls()` only knows about calls registered through the *plugin's* provider. Since the native `CallManager` uses its own provider, `activeCalls()` always returned an empty list — even when native CallKit was already displayed. The `active.isEmpty` guard therefore passed every time, and a second CallKit UI was presented.

Two providers, two UUIDs, two answer handlers. Tapping Accept on the native UI fired `CXAnswerCallAction` on the native provider; `CallEventActionCallAccept` on the plugin stream never fired (or fired for the wrong UUID). The call either disconnected immediately after answering or the CallKit UI stayed on screen permanently.

## Fix

**File**: `lib/main.dart` — `_firebaseMessagingBackgroundHandler`

On iOS, skip `FlutterCallkitIncoming.showCallkitIncoming()` entirely. The VoIP push + `AppDelegate` + `CallManager` own the CallKit UI. The FCM background handler's only job on iOS is to write call metadata to SharedPreferences so the answer flow can read it.

```dart
// BEFORE — always called FlutterCallkitIncoming.showCallkitIncoming() with an
// activeCalls guard that was always empty on iOS (plugin has no visibility into
// the native CXProvider used by CallManager).

final active = await FlutterCallkitIncoming.activeCalls();
if (active.isEmpty) {
  await FlutterCallkitIncoming.showCallkitIncoming(params);
}

// AFTER — iOS returns early after writing metadata only.
// Android keeps the flutter_callkit_incoming path unchanged.

if (Platform.isIOS) {
  await prefs.setString('pending_callkit_id', callId);
  return;
}
// Android: flutter_callkit_incoming shows the notification-based incoming call UI
await FlutterCallkitIncoming.showCallkitIncoming(params);
```

The unused `IOSParams` and `Uuid` imports (which were only needed for the removed iOS CallKit path) were also removed.

## How It Works

There is now exactly one `CXProvider` on iOS — the one inside `CallManager.swift`. Every CallKit lifecycle event (answer, end, audio activate/deactivate) flows through `CallManager`'s `CXProviderDelegate` and then to Flutter via the `com.getgabs/calls` method channel. The plugin's `CXProvider` is never invoked on iOS. Answer events come through `onNativeCallAnswered`; end events come through `onCallEndedNatively`. The plugin's `onEvent` stream is not used on iOS at all (already guarded by `setupCallKitEvents` skipping iOS).
