# M-6 — `cleanupCall()` does not remove `pending_from_user_id` — stale key persists

## Problem

`cleanupCall()` and the inline cleanup in the accept-call path removed 5 SharedPreferences keys but missed `pending_from_user_id`:

```dart
await prefs.remove('pending_call_id');
await prefs.remove('pending_callkit_id');
await prefs.remove('pending_call_session');
await prefs.remove('pending_caller_name');
await prefs.remove('pending_caller_number');
// ← 'pending_from_user_id' never removed
```

`pending_from_user_id` is written in the FCM background handler and in `onNativeCallAnswered` (via `storePendingNavigation`). It persists across calls. On the second incoming call:

- `_checkInitialCall` reads `pending_from_user_id` with the value from the *previous* call.
- If the call is from a different user, the backend receives an incorrect `from_user_id` in the answer request.
- In edge cases (e.g., the caller hung up and a new caller rang immediately), the previous caller's `from_user_id` could be sent to the new call's backend endpoint, causing an authorisation error or connecting to the wrong call.

## Fix

**File**: `lib/domain/services/whtasapp_calling_service.dart`

Add `pending_from_user_id` to both cleanup sites:

```dart
// In cleanupCall()
await prefs.remove('pending_from_user_id');

// In the inline accept-path cleanup
await prefs.remove('pending_from_user_id');
```

## How It Works

`pending_from_user_id` is read by `GlobalCallListenerService._handleCallAccept` to identify the caller. Once a call ends (or is rejected), this value is stale. Removing it at the same time as the other 5 keys ensures the next call always starts with a clean state and reads the correct `from_user_id` from the new push payload.
