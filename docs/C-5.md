# C-5 — No `uuid` in VoIP payload — random UUID per push causes CallKit UUID mismatch

## Problem

`AppDelegate.pushRegistry(_:didReceiveIncomingPushWith:)` read:

```swift
let rawUuidString = data["uuid"] as? String ?? UUID().uuidString
```

The server never included a `uuid` field in the VoIP payload, so every VoIP push generated a fresh `UUID().uuidString`. Meanwhile `_firebaseMessagingBackgroundHandler` on iOS also generated a UUID (previously from `Uuid().v4()`, or tried to read `pending_callkit_id` — but due to C-1 the read always returned empty and fell back to a new `Uuid().v4()`).

Result: the native `CXProvider` (in `CallManager`) registered the call under UUID-A, while any Flutter-side reference used UUID-B. When the call ended:
- `FlutterCallkitIncoming.endCall(callkitId)` passed UUID-B → native provider knew nothing about UUID-B → the native CallKit UI stayed on screen.
- `endNativeCall` from Flutter passed UUID-B → `CallManager.endCallProgrammatically(uuid:)` could not find UUID-B in `activeCalls` → no-op.

## Fix

### Server (`SendCallFcmNotificationJob.php`)

Add `ramsey/uuid` (already a Laravel transitive dependency) and generate a deterministic UUID v5 from `callId`. UUID v5 is deterministic — the same `callId` always produces the same UUID regardless of how many times the job runs.

```php
use Ramsey\Uuid\Uuid;

$stableUuid = Uuid::uuid5(Uuid::NAMESPACE_URL, $this->callId)->toString();

$dataPayload = [
    // ...existing fields...
    'uuid' => $stableUuid,   // same on VoIP push and FCM
];
```

This `uuid` field is included in both the FCM data payload and the APNs VoIP payload body.

### Native (`ios/Runner/AppDelegate.swift`)

Read the server-supplied `uuid` field first; fall back to `call_id`, then to a fresh UUID only as a last resort:

```swift
// BEFORE — always generated a new random UUID
let rawUuidString = data["uuid"] as? String ?? UUID().uuidString

// AFTER — prefers server-supplied stable UUID
let rawUuidString = (data["uuid"] as? String)?.lowercased()
    ?? (data["call_id"] as? String)?.lowercased()
    ?? UUID().uuidString
```

### Flutter (`lib/main.dart`)

Store the server-supplied `uuid` from the FCM payload, not the raw `callId`:

```dart
// BEFORE
await prefs.setString('pending_callkit_id', callId);

// AFTER
final serverUuid = message.data['uuid'] ?? callId;
await prefs.setString('pending_callkit_id', serverUuid);
```

## How It Works

UUID v5 is a hash-based UUID (SHA-1 of namespace + name). Given the same namespace (`Uuid::NAMESPACE_URL`) and the same `callId` string, it always produces the same UUID on any platform. The server generates it once; both the VoIP delivery path (AppDelegate) and the FCM delivery path (Flutter background handler) receive the same value. `CallManager.activeCalls` stores this UUID; `FlutterCallkitIncoming.endCall` and `endNativeCall` both reference the same UUID — end-call actions now correctly target the active call.
